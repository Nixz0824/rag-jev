# 0.14.0 · Jev 成为按需参与的决策层

> 这是 GitHub Release 的正文，由 `CHANGELOG.md` 的 `## 0.14.0` 段落导出。
> 在 Releases → Draft a new release → 选择标签 `v0.14.0` → 把下面横线之后的内容粘进说明框。
> 标题填：`0.14.0 · Jev 成为按需参与的决策层`

---

Jev 从「候选重排 + 回答自检」的后置决策组件，扩展成按需参与查询理解与检索规划的决策层：
**能确定的交给代码，只有语义不确定时才交给 Jev。**

### 架构

- 新增 **查询计划**（`query_plan.py`）：解析结果从普通 dict 升级为 `QueryPlan`，
  每个槽位带 `Slot(value, source, status, confidence, why, candidates)`。
  关键新增能力是 `Slot.closed` / `QueryPlan.resolved_deterministically()`：
  **确定性规则或别名命中的槽位对模型关闭**，这是「不把确定答案改成概率答案」的代码表达。
- 新增 **分类树**（`taxonomy.py`）：意图 / 模式 / 实体类型 / 技能 / 字段族。
  按真实语料分布建树（4995 chunk、2212 结构化行、30 版本）：`damage` 占结构化行 33%，
  因此字段层做两级「族 → 具体键」；`ability` 为空的有 3987 条，
  说明「技能未知」是常态，也是最值得语义补全的槽位。
- 新增 **语义路由策略层**（`routing.py`）：`jev.py` 只保留 transport 与 choice/noul 原语，
  分类表与路由规则不进入 `jev.py`。
- 会话新增 `query_plan` / `routing` / `jev_phases`，全部由真实执行产生，前端不再猜状态。

### Jev

四个角色按生命周期排列，每个角色都有 `called` / `bypassed` / `fallback` / `failed` 状态：

- **A 语义补全**：只对确定性解析留下的空槽提问，多个槽位合并成一次调用。
- **B 分层路由**：判断该去哪一块知识空间找；字段节点分两级（族 → 键）。
- **C 候选重排**：保留原有 `jev.rerank` 与 `MIN_RERANK_GAP = 0.15` 置信闸门。
- **D 证据判读**：保留原有 `jev.judge_many` 回答自检。

新增 `jev.classify_many`（多槽位一次调用）、`jev.shortlist`（在已收窄的候选里选实体）、
`jev.choose` / `choice_result`（choice 结果规范化）、`PHASES` / `book` / `phase_totals`（分阶段记账）。

### Retrieval

- **置信分叉**：把「采纳一个值」（`min_fallback_confidence = 0.35`）与
  「只此一种读法」（`commit_confidence = 0.60`）拆开。首选与次选接近时，
  采纳首选值的同时**另开一条竞争分支**，分别检索后合并候选。
  实测 `W 0.51 / 被动 0.47` 会走两条分支。
- **路径分数用几何平均**（`exp(mean(log p))`）而不是连乘，避免深路径天然吃亏；
  无可信节点的路径计 1.0（没有猜测就没有不确定性）。
- **保守路径**：只要语义决策收窄了搜索，就额外保留一条**无技能/字段过滤**的路径，
  保证误判只降低精度、不会让正确行不可达。
- **分支合并**用加权 RRF：`Σ score_branch / (60 + rank)`，权重为路径分数。
  这样「无过滤保守路径」因为候选最多而不会在平局中压倒高置信读法；
  常数与检索内核的 RRF 一致。
- `engine._candidate_indices` 支持 `field_keys` 集合过滤与 `ability="base"` 例外
  （base 表示「不按技能过滤」，而不是过滤空技能）。

### 前端

- 工作台新增**静态架构图**（数据层 / 查询理解 / 检索 / 决策 / 回答安全五层），
  Jev 节点统一琥珀金标记，确定性节点保持中性色，并给出图例。
- 新增**逐查询执行图**：每次提问后画出真实的阶段链、槽位来源、分叉情况、
  合并结果与 Jev 分阶段成本，`bypassed` 也显示原因。
- Jev 面板改成四段角色结构，并新增**分阶段成本/延迟 breakdown**；
  静态架构与实时执行分开呈现。
- 窄屏修复与实测：**320 / 360 / 390 / 414 / 480 / 720 / 900 / 1080 / 1440 全部无整页横向溢出**。
  修掉三个真实缺陷：`.console` 首列 320px 最小宽度在单列后仍生效、
  `#composer` 子项 `min-width:auto` 被 textarea 顶宽、
  回答里的公告 URL 在 `white-space: pre-wrap` 下不可断开；
  另外为窄屏固定底栏预留文档末尾空间（否则页尾内容被永久遮住）。
- 新增 `tools/check_viewport.py`：实测整页横向溢出（并指出元素）、底栏遮挡与页面 JS 报错，
  退出码可用于 CI；`tools/screenshot.py` 支持指定视口宽度与区块。

### Evaluation

- 新增 `tests/cases/routing_cases.json`（8 条：全确定 / 语义模糊 / 首选次选接近 /
  只问未知层级 / 无 key 对照 / 装备 / 跨版本聚合）与 `scripts/evaluate_routing.py`。
- **全部评测已用真实 Jev 跑通**（`TYPESAFE_API_KEY`），逐项复现已公布数字：
  - 盲测 78 题（hybrid+jev）：单点命中@1 **40/40**、数值 40/40、版本 26/26、汇总 14/14、
    拒答 8/8、越界 8/8、聚合 6/6、**回答自检 40/40**（16 次调用、$0.00225）
  - 同源 84 例：定点命中@1 21/23 → **22/23**、自检 **55/55**、Jev 首选 14/14、陷阱 18/18
    （37 次调用、$0.00362）
  - `evaluate_jev.py`：91 条可判定、改序 1（改对 1）、保留 90；排序对照 47/49 → 48/49
  - `evaluate_selfcheck.py`：注入检出 **24/24**、误报 0/24；对照 0.9625 vs 注入 0.0454
- **分层路由的实测结论（重要，分两步得出）**：
  1. 先用 `tests/cases/routing_cases.json`（8 例机制集）测：off 与 active **都是 7/8**，
     改善 0、损害 0。原因是那套题里 5 条不需要模型、2 条本来就能命中、1 条语料上不可判定 ——
     **结构上没有可提升空间**，因此它测不出收益（它现在只用于固定链路行为）。
  2. 另出 `tests/cases/routing_effect_cases.json`（**40 例效果集**，独立出题方依官方公告编写、
     出题时禁止读本项目语料，每题都满足「不筛技能时正确行会被挤到后面」）后再测：
     **BM25 口径 off 25/40 → active 28.3/40；生产默认的 hybrid 口径 off 26/40 → active 29.3/40**
     （**3 次独立评测**的均值：off 三次恒为 26，active 为 29.0 / 29.67 / 29.33）。
- **提升的边界**（与上面的数字同时成立）：
  - 命中@5 两种口径都是 **40/40** —— 路由改善的是**排序**，不是召回；
  - **损害不是 0**：改善稳定为 12 条，但**损害 1～3 条**（三次运行 3 / 1 / 2），必须与收益一起报；
    初版曾报「损害 0」，那是单次运行的运气，已更正；
  - 影响集中在 **5 条案例**上，40 条样本不足以支撑通用百分比收益，运行间波动约 ±0.5 条；
  - 12 条两种口径都答不对，归因后**均值 8.7 条是「技能认对、选错行」**（重排的残余错误）、
    2.3 条技能认错、1.0 条无有效信号；
  - **这套题只覆盖技能消歧这一条轴**：技能槽 39/40 开放，字段槽 **40/40 全被规则关闭**，
    因此「字段族的语义路由」本版本未测量。
- **修掉一个由这套题暴露的真缺陷**：公告里存在 `伤害增幅所需距离：525 → 未改动`
  这类「新值其实是说明文字」的行（全库 1 条），原先它被当作一次改动参与排序，
  还排在真正变了的那行前面，把「那根标枪飞得够远时额外伤害上限」顶掉。
  现在加载时标记（`new_value_is_remark`）：渲染时写明「公告注明未改动，数值未变」，
  重排时降到末位但**仍保留在候选里**。修完 off 与 active 各 +1，提升幅度不变。
- 新增 `scripts/attribute_routing_errors.py`：把失败案例归因为
  技能认错 / 技能对但选错行 / 无有效信号（**带 `--repeat`，报均值与各轮分布**，
  因为模型每轮重新判断），并落盘 `docs/Jev分层路由-失败归因.md`，用来区分
  「路由的锅」与「重排的锅」。
- 新增 `scripts/diagnose_rerank.py`（重排失败诊断：候选集 / 名次 / 同字段标签）与
  `scripts/measure_field_filter.py`（字段过滤逐条对照），把「技能认对、行选错」拆成
  `absent`（候选没进来）/ `below`（在但排后面）/ `tie-label`（标签太像）三类。
  实测 10 条失败中 **9 条是 `tie-label`** —— 正确行就在候选里、只是标签歧义，
  属于**题目措辞**而非引擎缺陷。
- **字段过滤的实验与结论**：把精确 `field_key` 过滤放宽为「同族 + 问题里真的出现了该字段词」
  （`RAGJEV_FIELD_WIDENING`，默认开）。依据：精确过滤在 40 例效果集上让 **5 条的正确行直接消失**、
  只让 1 条名次变好；整族放宽则因 durability 族有 9 个键而引入噪声（A/B：关闭 29/40 损害 3、
  开启 29.3/40 损害 2）。最终采用证据驱动的放宽——**只在问题自带该字段词时才纳入同族键**，
  它是精确过滤的严格超集，不会弄丢原本能取到的行；实测与关闭时差异在噪声内，
  因此登记为「不损害安全网」而非「提升」。开关保留，便于复测。
- 早先 fixture 口径跑出的 `off 5/8 → active 8/8` 是回放手写分布的结果，
  **没有在真实模型下复现**，已不再作为依据；相关约束已加测试
  （`kind: routing_effect` 的案例禁止携带 `expect.abilities`）。
- `--repeat N`：模型有随机性，单次结果不足以支撑结论；报告给出每轮命中、均值、
  逐轮不稳定案例，并区分**案例数**与**按轮次累计的条目数**（后者会被重复次数放大）。
- `--retrieval bm25|hybrid`：两种检索口径都能跑；hybrid 需要 18892 向量服务，
  索引不可用时**明确回退并提示**，而不是静默给出 0/40 这种看起来像结果的数据。

### Compatibility / fallback

- 新增 `RAGJEV_ROUTING_MODE` = `off` / `shadow` / `active`（默认 active）。
  `off` 完全等同 0.13.0 行为；`shadow` 照常判断并记录但不影响检索，用于对照。
- 没有 key 时链路完整可用：确定性解析、元数据过滤、混合检索、模板渲染全部照常；
  语义补全 / 分层路由 / 重排 / 自检被跳过，**每一处跳过都写进轨迹与阶段账本**。
- **修掉 key 读取的静默失败**：`AGENTS.md` 说明 key 可放在 `runtime/jev-key.txt`，
  但加载器只认 `TYPESAFE_API_KEY=…` 形态，放裸 key 时静默返回空字符串 ——
  链路照常运行、只是永远降级。现在两种形态都支持。
- 预算上限：每次提问最多 2 次理解类调用、20s 超时、`beam_width = 2`、`max_depth = 4`。
- 区分「没有 key」与「本次不需要 key」：全部槽位已确定时状态是 `bypassed` 而不是 `fallback`。

### Tests

- 196 项（新增 77 项）：查询计划与分类树契约 22 项、语义路由行为 40 项、
  评测完整性 11 项，另含 bypass / beam / budget / shadow / 无 key 降级 /

### Known limitations

- **分层路由的收益幅度有限**：40 例效果集上 off 24/40 → active 27.3/40（只有 active 答对 4 条、
  只有 off 答对 0～1 条、损害 1～3 条），**不改善召回**（命中@5 两种口径都是 40/40），影响集中在 5 条案例上；
  样本量不足以支撑「通用百分比收益」的说法。首次用 8 例机制集**没有测到提升**，
  原因是那套题结构上没有可提升空间 —— 两次结果与原因都保留在报告里。
- **12 条两种口径都答不对**：归因后 8 条属于「技能认对、选错行」（重排的残余错误），
  说明当前瓶颈更多在重排而非路由；这一点没有靠调路由参数去掩盖。
- **样本量小**：能触发路由的只有 3 条，任何比例都不能外推成收益幅度。
- **路由确实会把对的题改错**：3 次独立评测的损害为 3 / 1 / 2 条，不是 0。
  收益（+3～4 条）与代价（1～3 条）必须一起看；净收益仍为正，但「零代价」的说法已被更正。
- **保留 0.12.0 的负面结论**：元数据过滤后候选常常只有 1—6 条，Jev 重排空间很小
  （91 条里只改 1 条）。0.14.0 没有推翻它 —— 分层路由是把 Jev 前移到检索**之前**，
  而不是让重排变得更重要。
- 字段族划分是人工按语料分布归类的，不是学出来的；新增字段需要手工归族
  （`tests/test_query_plan.py` 会强制这一点）。
- 实体消歧仍偏弱：`subject_shortlist` 靠 difflib 与包含关系，候选常为空，
  因此「对象完全说不清」的问题仍会走追问而不是语义选择。
